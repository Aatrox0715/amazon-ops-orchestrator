## 单环执行 vs 全链路

**用户只想要一环** → 只跑那一环，但要先检查上游：

- 上游产出已在项目档案里 → 直接读 `output.json`，不重复劳动
- 上游缺失 → 告诉用户："这一环最好有 X 的结论做输入。要么先跑 X，要么我用降低精度的方式先跑（说明降什么）"

**用户要全链路** → 按依赖顺序连跑，每到闸门停下。

**中途插入** → 用户从第 6 环直接杀进来要改文案，先读项目档案确认词库和卖点还在，直接接上。

## 状态标记规则（实测踩过的坑）

**跳过的前置环节必须显式标 `skipped`，不能留 `pending`。**

`current_stage` 的算法是"第一个非 done / skipped 的环节"。若用户从第 2 环开始、
而第 1 环仍是 `pending`，状态就会显示"当前环节 01"，与事实矛盾，后续环节会被误导。

```bash
# 用户只给 ASIN 直接做竞品拆解 → 第 1 环本次不执行，必须显式标掉
python state.py stage <代号> 01 skipped
```

语义区分：

| 状态 | 含义 |
|---|---|
| `pending` | **计划要做，但还没做** |
| `skipped` | **本次流程不执行这一环** |

用户后续若想补做，把 `skipped` 改回 `pending` 即可，档案不丢。

## 迭代闭环的写法

第 10 环的复盘结论**不能只写在新文件里**，必须显式标注"要回写哪一环的哪个字段"：

```json
{
  "iteration_targets": [
    { "stage": "06", "field": "title", "action": "replace",
      "reason": "广告搜索词显示 X 词转化高但标题未覆盖" },
    { "stage": "07", "field": "image_plan", "action": "add",
      "reason": "差评集中在尺寸感知，需补尺寸对比图" }
  ]
}
```

用户批准后，回到对应环节执行修改，并在 `_state.json` 的 `revision_history` 记一笔。
