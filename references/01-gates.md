# 三级确认闸门规则

## 判定原则

闸门级别由两个维度决定：**不可逆性** × **对外可见性**。

| 级别 | 判据 | 行为 |
|---|---|---|
| 🔴 P0 | 做了就改不回来，或对外可见，或要花钱 | **停下，等你明确批准**。未获批准不得推进，不得"先做了再说" |
| 🟡 P1 | 影响大但能改回来 | **停下，给方案让你选**。给出 2–3 个选项 + 各自代价 |
| 🟢 P2 | 随时可重做，只有内部可见 | **自动做完，汇报结果**。不停顿 |

**关键**：闸门级别看的是**动作性质**，不是环节编号。同一环节里可能既有 P2 动作也有 P0 动作。

## P0 清单（必须停下等批准）

以下动作**一律**需要用户明确说"可以"才能执行：

| 动作 | 为什么是 P0 |
|---|---|
| Listing 定稿并准备上架 | 上架后改动影响排名与历史数据 |
| 任何对 Amazon 后台的**写入**操作（SP-API / 卖家后台） | 直接影响真实账号 |
| 广告活动创建、预算调整、竞价修改 | 直接花钱 |
| 任何对外发送（邮件 / 消息 / 提交申诉 / 发布内容） | 对外可见，无法撤回 |
| 促销活动提报（Coupon / Deal / PED） | 花钱 + 影响价格历史 |
| 删除或覆盖已有产出物 | 丢历史，不可逆 |

**P0 的正确处理方式**：

1. 把所有待执行动作**完整列出**（改哪个字段、从什么改成什么）
2. 标注影响面（影响哪些产品/活动/金额）
3. 说清不可逆的点在哪
4. **停下等明确批准**——"好的""继续"这类模糊回应不算批准，要确认到具体动作

## P1 清单（停下给方案）

| 动作 | 为什么是 P1 |
|---|---|
| 关键词库定稿 | 决定了后续所有文案与广告的用词 |
| Listing 文案初稿 | 后续视觉与体检都基于它 |
| 定价策略 | 影响利润与竞争力，但可改 |
| 视觉素材方案 | 制作成本高，方案定错浪费 |
| 广告架构设计 | 结构定错后面调起来麻烦 |
| 迭代修改方案 | 会触发多环节联动 |
| 数据源级别降级决定 | 精度取舍，用户应知情 |

**P1 的正确处理方式**：

```
【需要你定】关键词库分层方案

方案 A｜激进覆盖（推荐度：中）
  主攻词 12 个，长尾 180 个，否定词 40 个
  代价：覆盖广，但前期广告预算分散，需要 2–3 周才收敛

方案 B｜集中爆破
  主攻词 5 个，长尾 60 个，否定词 25 个
  代价：起量快，但长尾流量漏掉，后期需补

方案 C｜保守铺量
  ...

你选哪个？或者告诉我你的预算量级，我按预算倒推。
```

## P2 清单（自动放行）

- 市场调研与数据整理
- 竞品拆解分析
- 评论与 VOC 分析
- 竞品数据抓取与清洗
- 内部草稿、思路梳理
- 报告排版与格式化
- 时效核对与来源补标

这些做完**直接汇报结果**，不需要事先批准。但汇报时要说清做了什么。

## 闸门的例外

**用户显式授权连跑**时（"这条链一路跑完别问我"），P2 和 P1 可自动推进，但 **P0 仍然必须停**。

原因：P1 做错了能改；P0 做错了要么花钱、要么对外、要么丢历史。授权连跑 ≠ 授权越权。

## 汇报闸门的写法

到闸门时，汇报必须包含四要素：

1. **做完了什么**（产出物路径）
2. **关键结论**（3 条以内，带来源）
3. **缺什么**（L3 字段清单，如有）
4. **下一步是什么 + 需要你定什么**
